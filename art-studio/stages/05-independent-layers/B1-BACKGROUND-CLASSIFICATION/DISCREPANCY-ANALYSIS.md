# B1.1 — Анализ расхождения 6 717 / 3 841

## Короткий ответ

Это **не два измерения одной величины**. `3 841` — историческое количество пикселей, которые stage-04 сделал прозрачными в **4 запертых лакунах**. `6 717` — количество **непрозрачных** пикселей сохранённого `work-cutout.png`, чей RGB близок к построчному фону `IMG_4038`. Множества разделены alpha: первое `alpha<128`, второе `alpha>=128`, пересечение **0 px**. Противоречия нет; для дальнейшей работы корректной **входной выборкой классификации** является `6 717 px / 782 компонента`, а `3 841` — только исторический отчёт об уже удалённом.

---

## 1. Метод stage-04 (`SLICE-MAP.md`, `MANIFEST.json`)

1. Билинейная модель фона по четырём углам, усреднение 12×12: TL `(42, 30, 63)`, TR `(43, 31, 66)`, BL `(77, 55, 108)`, BR `(79, 57, 110)`.
2. Грубая маска «похоже на фигуру» `L1 ≥ 58`, морфологическое закрытие `Disk:2`.
3. BFS/flood-fill **только от границы холста**: фоном считается лишь связная с краем область; внутренние тёмные зоны сохраняются.
4. Компонентный анализ запертых областей: **4 связные области со средним L1<19**, всего **3 841 px**, удалены из alpha как остатки фона между прядями. Ещё **49 225 px** тёмной одежды в полосе `L1 19…57` сохранены. Независимый пересчёт по документированным округлённым углам даёт **49 228 px** в этой полосе и **3 424 px** в `L1≤18`; разница 3 px против 49 225 объясняется округлением углов/порогом alpha и не влияет на вывод.
5. Сглаживание края `blur 0x0.6`.

Пересчёт по сохранённому `work-cutout.png` / `alpha-mask.png` с порогом `alpha<128` даёт **3842 px в 4 компонентах**:

| Лакуна | Px | Bbox | Ср. L1 к модели |
|---|---|---|---|
| ST04-HOLE-01 | 1470 | [167,454–196,553] | 17.78 |
| ST04-HOLE-02 | 1442 | [652,453–681,552] | 18.32 |
| ST04-HOLE-03 | 488 | [261,553–283,608] | 18.94 |
| ST04-HOLE-04 | 442 | [530,498–543,557] | 18.45 |

Разница **1 px** (`3842` против `3841`) остаётся документально неразрешённой: скрипт исходной генерации stage-04 отсутствует, поэтому нельзя достоверно приписать её конкретному порогу, округлению `blur 0x0.6`, правилу включения границы или способу подсчёта в историческом отчёте. Перебор порогов показывает чувствительность результата (`alpha<127` и `<128`: `3842/4`; `<64`: `3593/7`; `<16`: `3109/5`), но не доказывает причину. Исторический файл не менялся. Координаты лакун соответствуют `PLAN.md §2`: между прядями у рук/плеч, `y≈453…608`.

## 2. Метод E3 / E3.5 (`build_assembly.py`, `ISSUE-MAP.json`)

```
for each row y:  bg = RGB(IMG_4038[y, x=0])
for each opaque pixel p (work-cutout.alpha >= 128):
    if max-channel |RGB(work-cutout[p]) - bg| <= 10: candidate
4-connected components of candidate pixels
```

Итого **6717 px / 782 компонентов**, bbox всех `[141, 70, 707, 1094]`. Это **построчная** модель цвета фона, а не билинейная; учитывается горизонтально-постоянный цвет строки `x=0`. Порог **±10 по максимальному каналу**, а не L1. Связность используется только для разбиения на компоненты, а не для отделения внешнего фона. E3 честно назвал результат «фоново-окрашенной непрозрачностью / глубокими тенями», а не удаляемым фоном.

## 3. Почему числа не должны совпадать

| Причина | Stage-04 `3 841` | E3/E3.5 `6 717` |
|---|---|---|
| Состояние alpha | удалённые `alpha<128` | сохранённые `alpha>=128` |
| Модель фона | билинейная по 4 углам | построчная `x=0` |
| Мера близости | средний L1 компоненты `<19` | max-channel `<=10` у пикселя |
| Отбор | 4 запертые связные области после flood-fill | все непрозрачные цветовые совпадения, 782 компонента |
| Что считается | площадь уже убранных лакун | площадь кандидатов, требующих классификации |
| Назначение | отчёт об очистке alpha | стресс-диагностика остаточной фоново-окрашенной непрозрачности |

Дополнительно: **4308 px** из 6 717 попадают в сохранённую тёмную полосу `L1 19…57`, а **2409 px** — в фоноподобную `L1≤18`. То есть 6 717 заведомо включает тёмную ткань, складки, тени и контуры; см. [00-overview-map.png](diagnostics/00-overview-map.png), [07-closeup-shoulders.png](diagnostics/07-closeup-shoulders.png), [08-closeup-clothing.png](diagnostics/08-closeup-clothing.png).

## 4. Какой результат корректен для дальнейшей работы

- `3 841` корректен **как исторический факт** stage-04: столько пикселей было переведено в прозрачность. Не использовать как цель B1.2 и не вычитать из 6 717.
- `6 717 / 782` корректен **как полный набор кандидатов** для B1.1: именно его классифицирует этот отчёт. Это не «список на удаление».
- После классификации реальными кандидатами на будущую тестовую очистку остаются только подтверждённые визуально `CONFIRMED_BACKGROUND` (4 / 3366 px) и, после ручной проверки, часть `LIKELY_BACKGROUND` (9 / 1349 px). `CHARACTER_PIXEL`, `ANTIALIAS_EDGE`, `AMBIGUOUS` удалению не подлежат.
- Никакое удаление не разрешено в B1.1. B1.2 требует отдельного явного разрешения и визуального подтверждения пользователем.
